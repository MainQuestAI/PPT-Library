# PPT Library v2.0.1 稳定化实施方案

**分支：** `codex/v2.0.1-stabilization`  
**基线：** `origin/feat/v1.5-iteration@6f624a6` + Deck Master 契约回带 `bf6ca04`  
**目标版本：** `2.0.1.dev0`  
**审查日期：** 2026-07-13

## 1. 结论与成功标准

本轮把 v2.0 的“模块已存在”提升为“核心链路可验证、失败可感知、发布可追溯”。完成边界如下：

1. 已确认的 P1 风险全部有回归测试，P2 风险中影响发布可信度和用户主流程的项目同步收口。
2. `init_db → index_file → identity/FTS/vector → hybrid search → rerank → trace → search-response.v2` 在真实数据库上跑通。
3. Agent/装配失败返回非零退出码；失败不计入成功使用量；人工复核、确认、跳过和血缘字段保持真实。
4. Workbench 能在浏览器打开，默认限制本机访问；写操作经过来源校验、权限、workspace 和审计链。
5. 基础安装、Workbench extra、all-extras 依赖状态均可被能力探测和 CI 正确识别。
6. pytest、ruff、mypy、coverage、依赖审计、构建产物扫描、release check、CLI smoke、浏览器 QA 全部通过。
7. Schema v6 幂等迁移保留 v5 数据，并把旧的 slide 外挂文件记录与 canonical 资产实体拆成独立表。

## 2. 范围决策

### What already exists

| 子问题 | 已有能力 | 本轮处理方式 |
|---|---|---|
| 密钥保护 | `config.SENSITIVE_KEYS`、`settings_summary` | 扩充统一敏感字段注册表，并复用到 config/doctor 输出 |
| PPTX 安全 | `pptx_safety.py`、`defusedxml`、connector symlink 防护 | 将同等边界应用到 source scan、索引和 QA 临时目录 |
| SQLite 并发 | ADR 003 已确定 Single Writer | 把真实 source 批量索引改为预初始化、并行提取、受控写入与单文件失败隔离 |
| 稳定身份 | `asset_identity_map`、`slide_revisions`、legacy slide id | 搜索通过 join 使用现有映射，不新增平行身份字段 |
| 两类资产 | v5 中 legacy 外挂文件与 canonical 资产都声明为 `slide_assets` | v6 将 legacy 数据迁到 `slide_artifacts`，`slide_assets` 专用于 canonical 资产 |
| 搜索组件 | FTS5、SqliteScanBackend、RRF、reranker、ranking_v2、TraceBuilder | 串成一条真实应用服务链，并输出 v2 契约 |
| 契约 | 7 个 JSON Schema、Contract Registry、统一错误码 | 采用标准 Draft 2020-12 校验器，保留兼容 alias |
| Workbench | FastAPI API、RBAC、workspace、audit、SSE、HTML shell | 在现有服务层上补安全边界和真实页面/API 联动 |
| 发布 | release_check、GitHub Actions、Hatch 构建 | 增加开发版/稳定版血缘判断、显式产物 allowlist 和安全门禁 |

### NOT in scope

- OIDC、企业 SSO 和外部身份供应商：本轮交付本机安全默认值和可扩展 token 边界；完整身份平台留给独立产品迭代。
- Postgres、Redis、Celery：现有 local-first 与 Single Writer 架构足以解决本轮问题。
- ANN 专用向量数据库：本轮接通现有 SQLite scan；数据规模门槛达到后再做可量化选型。
- Workbench 全量视觉重设计与远程多租户：只补可用页面、错误状态、交互、安全反馈和固定 default workspace fail-closed。
- 一次性拆解 2871 行 CLI：只抽取本轮直接涉及的 handler 或 helper。
- 开源发布、tag、push、PR 和部署：本轮只建立可发布状态与验证证据，发布动作需单独授权。

```text

      │
      ├─ JSON contract validation
      ├─ query embedding when provider is available
      ├─ FTS5 lexical ─┐
      ├─ SQLite vector ├─ RRF fusion ─ rerank ─ business score ─ query trace
      └─ fallback──────┘                                      │

      │
      ├─ capability negotiation + stable aliases
      ├─ explicit failure exit codes
      ├─ workspace-aware permission / origin guard

Release candidate
      └─ tests → lint/type → coverage → dependency audit → build allowlist
             → stable-version public-history gate → CLI/browser smoke
```

## 4. 审查结论

### Architecture Review

1. **P1，置信度 10/10：v2 搜索模块没有接入真实 v5 数据模型。** `fts_search.index_from_slides` 读取 `slides` 不存在的身份列，`vector_backend` 读取不存在的 `embeddings` 表。决策：复用 `asset_identity_map` 与 `slides.embedding`，不建第二套数据表。
2. **P1，置信度 10/10：Workbench 的安全声明与运行行为不一致。** 决策：默认仅 loopback；非 loopback 必须显式 token；静态 token 视为整个本地素材库的管理员凭据；写操作校验 Origin/CSRF 等效令牌、RBAC、单进程 workspace namespace；所有写操作先写 intent audit，再执行业务并记录结果。workspace 不提供多租户数据隔离。
3. **P1，置信度 10/10：真实 v5 数据库中两类 `slide_assets` 发生表名冲突。** 决策：升级 Schema v6，legacy 表迁到 `slide_artifacts`，canonical 表保留 `slide_assets`，按列形状幂等兼容已有库。
4. **P1，置信度 10/10：删除和内容变更没有统一派生状态生命周期。** 决策：v6 重建依赖表并明确 CASCADE、SET NULL、RESTRICT；建立事务内失效 helper 供索引、prune、reindex 共用。
5. **P1，置信度 10/10：稳定版本与公开血缘缺少机器门禁。** 决策：开发分支使用 `2.0.1.dev0`；稳定版本构建自动要求 `public/main` 为祖先。

### Code Quality Review

1. **P1，置信度 10/10：敏感字段维护分散且漏掉 `embedding_api_key`。** 决策：单一注册表驱动“禁止写入 + 输出脱敏 + 明文迁移提示”。
2. **P1，置信度 10/10：Contract Registry 只做顶层手工校验。** 决策：使用 `jsonschema` Draft 2020-12，错误转换为现有 `ContractError`。
3. **P1，置信度 10/10：`--probe`、Workbench capability 和 `ft5_search` 名称会返回错误事实。** 决策：运行时依赖探测、带超时 provider probe、稳定能力名加兼容 alias。
4. **P1，置信度 10/10：装配/Agent 多条错误路径被吞掉。** 决策：统一 result/exit-code 规则，失败不写成功 usage，人工复核与确认状态进入结果契约。
5. **P1，置信度 10/10：Deck Master 通过数组位置重建 beat 引用。** 决策：筛选时携带稳定 beat/page task identity，禁止二次按位置配对。

### Performance Review

1. **P1，置信度 10/10：每个并行 worker 都执行 DB 初始化和 WAL 变更。** 决策：线程池前单次初始化；worker 连接设置 busy timeout；单文件异常隔离。
2. **P2，置信度 10/10：FTS BM25 分数取反后升序，强匹配会落后。** 决策：统一“分数越高越好”的内部契约并锁定排序测试。
3. **P2，置信度 9/10：reranker timeout 参数没有生效。** 决策：本地 provider 直接执行；潜在阻塞 provider 在受控 executor 中执行并超时降级。
4. **P2，置信度 8/10：SQLite vector scan 会加载全部向量。** 决策：本轮增加维度过滤和分批读取；ANN 继续由规模 benchmark 触发。

## 5. 失败模式与用户反馈

| 失败模式 | 测试 | 处理 | 用户可见结果 |
|---|---|---|---|
| symlink 指向 source root 外 | 有 | 拒绝并记录路径 | 明确错误，不扫描外部文件 |
| fresh 目标缺专属 sentinel | 有 | 拒绝删除 | 明确说明保护原因 |
| 并行单文件 DB 锁/坏文件 | 有 | 重试/隔离该文件 | 批次完成并列出失败文件 |
| 内容变更后旧摘要或向量残留 | 有 | 同事务失效 | 搜索只返回当前内容 |
| provider 探测超时 | 有 | 标记 unavailable | capability 给出原因和恢复建议 |
| reranker 超时 | 有 | 降级到 fused score | 结果可用，trace 标记 fallback |
| 无效契约 | 有 | 退出 1 | `_errors` 含稳定错误码与路径 |
| 装配人工复核未通过 | 有 | 阻止完成态 | CLI/Workbench 显示待复核 |
| 非 loopback 无 token | 有 | 拒绝启动 | 明确安全配置提示 |
| 稳定版来自开发历史 | 有 | release check 失败 | 给出干净 public snapshot 指引 |

## 8. 终审补充与修复结果

实现完成后的独立终审又复现出 11 个高置信缺口，均已加入回归测试：

1. watcher 的文件删除竞态会终止长期监听；现已把 `stat` 竞态收敛为可重试的不稳定文件。
2. wildcard 远程绑定无法接受真实 LAN Origin；现要求显式 `--cors-origin`，并严格校验 Origin 格式。
3. Workbench 缺少 Host 白名单；现已拒绝 DNS rebinding 风格的恶意 Host。
4. 写入成功与审计连接异常之间存在空窗；现先持久化 intent，业务执行后再记录成功或失败结果。
5. 血缘循环和深度截断会漏掉终点节点；现保证节点数恒等于边数加一。
6. v2 搜索数组过滤、`page_role`、`review_state`、`include_versions` 与契约不一致；现已统一 schema、示例和实现。
7. 过滤发生在固定召回窗口之后会漏掉合法结果；现按需扩窗，直到满足数量或覆盖全部候选。
8. embedding provider/model/dimension 变化不会触发重建；现把 embedding signature 纳入增量跳过条件。
9. annotator、metadata 和 prune 没有同步 FTS；现统一刷新或删除搜索文档。
10. v6 迁移会静默吞掉跨 canonical 的 revision 冲突，并可能提交调用方事务；现冲突时安全中止，幂等调用保留外层事务。
11. 稳定版历史与构建产物只检查路径；现限制为 `public/main` 的干净单提交快照，并扫描 sdist/wheel 的敏感内容。

本轮保留的明确边界：远程 bearer token 是整个单库的共享管理员凭据；`workspace_id` 只承担单进程命名空间。多人角色、数据级租户隔离和原生 TLS 进入 v3.0 的独立决策。

## 9. 后续迭代目标

后续路线按业务收益和量化触发条件推进，当前不预埋新框架。

### v2.1：Agent 与 Workbench 产品闭环

- 业务目标：让非技术用户能在一个界面完成“检索、筛选、复核、确认、追溯”，并让 Agent 调用失败时给出可执行的恢复动作。
- 重点范围：补齐 v2 CLI 的兼容参数策略；统一批量复核和恢复入口；完成 Workbench 视觉与可用性专项；清理 SQLite 连接生命周期告警；把关键错误码转成面向用户的解决建议。
- 验收门槛：核心任务浏览器成功率不低于 95%；失败场景均有恢复路径；连续 1,000 次本机任务无连接泄漏告警；Agent 契约回归全绿。

### v2.2：规模化检索决策

- 业务目标：在素材库扩大后仍保持可预测的搜索速度和结果质量。
- 决策前置：分别用 1 万、5 万、10 万页真实或等价数据测量 p50/p95 延迟、内存、召回率和索引时间。
- 选型触发：只有当 SQLite 向量扫描在目标设备上持续超过 p95 500ms，或内存占用超过可接受预算，才评估 ANN 引擎；选型必须同时比较迁移复杂度、离线可用性和结果可解释性。
- 验收门槛：目标规模下 p95 搜索延迟不高于 500ms，关键页 Recall@10 不低于当前基线，降级路径保持可用。

### v3.0：团队协作与远程部署

- 业务目标：满足多人共享素材库、分角色复核和远程访问的企业场景。
- 启动条件：出现明确的多用户付费需求，且本机单管理员模式已验证稳定。
- 候选范围：OIDC/SSO、真实用户与角色映射、数据级 workspace 隔离、原生 TLS、集中任务队列和运维审计。当前远程 HTTP 仅用于可信网络，跨网络访问需要 TLS 反向代理或 SSH 隧道。
- 验收门槛：权限隔离测试、租户越权测试、灾备恢复和完整审计链全部通过后，才开放远程多人模式。
